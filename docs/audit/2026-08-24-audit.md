# Agnostik Security Audit — 2026-08-24 (v1.3.7 P(-1) hardening pass)

**Pass type:** P(-1) scaffold/hardening sweep per CLAUDE.md
§"P(-1): Scaffold / Project Hardening" + §"Security Hardening (before
every release)".
**Scope:** all `src/*.cyr` at the v1.3.6 tag (`2917781`), plus the CI
workflows and the benchmark/test harnesses.
**Toolchain:** cyrius `6.5.35` (pin unchanged from v1.3.6).

This was a full sweep rather than a diff review: v1.3.5 and v1.3.6 were
toolchain-refresh patches with no library-logic change, so the last audit
of the *source* was 2026-06-01 (v1.3.0). Six findings are new
(**F-014**..**F-019**), two long-standing backlog items are confirmed and
quantified (**F-020**, **F-021**), and several previously-suspected
problem areas were checked and found **sound** — those negative results
are recorded below because they are the expensive part of an audit and
should not be re-derived next cycle.

Four of the new findings are repaired in v1.3.7. Two (**F-018**,
**F-021**) require *additive public API* and are pinned to **v1.4.0**:
adding public functions in a patch release would violate the project's
own versioning discipline, and the gap is a completeness defect rather
than a live vulnerability.

## Threat model

Unchanged from prior audits. Agnostik is the shared type vocabulary
consumed by every AGNOS component (daimon, hoosh, agnoshi, aegis,
argonaut, sigil, ark, kavach, stiva, nein, yukti). The attack surface is
**untrusted JSON / version / UUID / traceparent input** crossing the
serde boundary into agnostik parsers; output flows back as
`Result<value, AgnostikError>` or typed structs. The only syscall
surface touching external state is the CSPRNG (`getrandom` /
`/dev/urandom`) and `stderr` (fatal message).

One threat-model note this pass sharpens: agnostik's *identifier* types
(`agent_id`, `user_id`, `trace_id`, `span_id`) back authorisation
decisions in aegis and sigil, and its *trace context* is propagated
across service boundaries by stiva. So a defect in entropy handling or
in traceparent validation is not merely a correctness bug — it is a
security-relevant one, which is why F-014 and F-015 are rated as they
are despite needing unusual conditions.

## Findings

### F-014 (MEDIUM) — `_fill_random` error sentinel neither exits the loop nor stays in bounds

`src/types.cyr`, `/dev/urandom` fallback inside `_fill_random`:

```cyrius
var off = 0;
while (off < n) {
    var r = syscall(0, fd, buf + off, n - off);
    if (r <= 0) { off = 0 - 1; }     # intended: "give up"
    else { off = off + r; }
}
syscall(3, fd);
if (off == n) { return 0; }
```

`off = 0 - 1` was clearly meant to abandon the loop. It does not.
**Cyrius compares signed** — verified directly: `(0 - 1) < 16` evaluates
true — so `off < n` remains true and the loop runs again with

- destination `buf + (0 - 1)` — **one byte before the buffer**, and
- length `n - (0 - 1)` = **n + 1** bytes.

Two distinct failure modes:

1. **One-byte heap underflow write.** If the retried `read(2)` succeeds
   it writes `n + 1` bytes starting at `buf - 1`, corrupting the byte
   before the allocation and shifting all `n` random bytes by one
   position. `off` then becomes `-1 + (n + 1) = n`, the loop exits, and
   `off == n` reports **success** — so the caller receives a
   silently-misaligned identifier and no error.
2. **Non-termination.** If reads keep failing, `off` stays `-1` forever
   and the loop never exits, so the deliberate fail-loud path
   (`stderr` + `exit(70)`) is never reached. A library call hangs.

**Reachability:** public — `agent_id_new()` / `user_id_new()` /
`span_id_new()` all funnel here. It requires `getrandom(2)` to not return
exactly `n` (old kernel, `ENOSYS`, seccomp filter, or signal
interruption) *and* a transient `/dev/urandom` read failure. Not
attacker-triggerable, hence MEDIUM rather than HIGH — but the fallback
exists precisely for degraded environments, which is where it would run.

**Fix (v1.3.7):** exit via an explicit flag, and report success off the
flag rather than off the offset. `break` is unreliable in a Cyrius
`while` carrying `var` declarations, so flag + `continue` is the
idiom the project mandates:

```cyrius
var off = 0;
var failed = 0;
while (off < n) {
    var r = syscall(0, fd, buf + off, n - off);
    if (r <= 0) { failed = 1; off = n; continue; }
    off = off + r;
}
syscall(3, fd);
if (failed == 0) { return 0; }
```

**Regression test:** `tests/tcyr/test_v137_hardening.tcyr` exercises the
control flow through a faithful replica with a scripted `read` result
(forcing a real `getrandom` failure from a test is impractical), and
pins the signed-comparison fact the bug depended on — so if a future
toolchain made `<` unsigned, the guard flips rather than silently
making the removed sentinel safe again.

### F-015 (MEDIUM) — traceparent accepted all-zero trace-id and parent-id

`src/telemetry.cyr`, `tctx_from_traceparent`. W3C Trace Context declares
an all-zero `trace-id` (32 zeros) and an all-zero `parent-id` (16 zeros)
**invalid**, and requires implementations to ignore such a traceparent
and start a new trace. Both parsed successfully, verified empirically:

```
00-00000000000000000000000000000000-00f067aa0ba902b7-01   -> Ok
00-4bf92f3577b34da6a3ce929d0e0e4736-0000000000000000-01   -> Ok
```

**Failure scenario:** an upstream service (or an attacker able to set
headers) sends an all-zero id. agnostik accepts it, stiva propagates it,
and every span in the trace shares a reserved sentinel id — collapsing
distinct traces together in the backend and making trace-scoped
correlation (including any audit correlation keyed on trace_id)
unreliable. Because agnostik is the *shared* implementation, the defect
is uniform across all eleven consumers.

**Fix (v1.3.7):** reject both, via a new private `_all_zero_bytes`
helper. The check is "all bytes zero" and not "leading zeros" — a
trace-id of `0…01` remains valid and is covered by a test.

### F-016 (MEDIUM) — traceparent version field never validated

Same function. The parser checked the three `-` delimiters at offsets 2,
35 and 52 but never looked at the 2-char version at offsets 0–1. So a
non-hex version parsed, and version `ff` — which the spec explicitly
forbids — was accepted:

```
zz-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01   -> Ok
ff-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01   -> Ok
```

**Fix (v1.3.7):** require both version chars to be hex and reject `ff`.
A valid hex version above `00` is still accepted — the spec requires
forward compatibility for the fields an implementation understands, so
`01-…` must parse. Both directions are tested.

### F-017 (LOW) — uppercase hex accepted on the traceparent path

Same function. W3C Trace Context mandates **lowercase** hex throughout
the header; uppercase makes the traceparent invalid. agnostik accepted
it at every position, because the shared `_hex_nibble` helper accepts
`A`–`F`:

```cyrius
if (ch >= 65 && ch <= 70)  { return ch - 55; }   # 'A'-'F'
```

That acceptance is **correct** for the helper's other caller: JSON's
four-hex-digit `\u` escapes, where RFC 8259 permits either case. This is
a direct consequence of the v1.3.0 refactor that merged
`_json_hex_digit` into `_hex_nibble` — a good de-duplication that
quietly coupled two callers with different case rules.

**Fix (v1.3.7):** enforce the case rule at the W3C boundary
(`tctx_from_traceparent`) rather than tightening the shared helper, which
would have broken conforming JSON input. A test asserts JSON `\u`
escapes remain case-insensitive, to stop a future "simplification" from
pushing the check back down into the helper.

Rated LOW rather than MEDIUM: unlike F-015 the resulting context is
internally consistent and round-trips, so the impact is interop
strictness rather than trace corruption.

### F-018 (MEDIUM, contract) — no enum has a `*_parse()` counterpart

CLAUDE.md §"Key Principles": *"All public enums must have `*_name()`
(string representation) and `*_parse(s)` (roundtrip)."*

Measured across `src/`:

| | count |
|---|---|
| enums declared | 58 |
| `*_name()` functions | 54 |
| enum `*_parse()` functions | **0** |

The only `_parse` symbol in the library is the private `_json_parse`;
the five `*_from_str` functions cover ID and version types, not enums.
So the stated roundtrip guarantee does not hold for **any** enum in the
type vocabulary.

**Failure scenario:** a consumer deserialising an `AgentStatus`,
`ClassificationLevel`, `AuditSeverity` or `LlmProvider` from a config
file or wire payload has no library-provided way back from the string
form, so each of the eleven consumers hand-rolls its own string→enum
mapping. That directly defeats agnostik's stated purpose ("Own the
stack — consumers should not redefine these"), and divergent hand-rolled
mappings across components are exactly how two services come to
disagree about what `"restricted"` means.

**Not repaired in v1.3.7.** Adding ~54 public functions is additive API
surface (`docs/api-surface.snapshot` would move from 871 to ~925), which
belongs in a **minor**, not a patch. Pinned to **v1.4.0** with a
concrete plan in `docs/development/roadmap.md`: generate `*_parse` for
every enum that has a `*_name`, make each one exact-roundtrip against
its `_name` output, and add a single table-driven test asserting
`parse(name(v)) == v` for every variant of every enum, so the invariant
is enforced mechanically rather than per-enum.

### F-019 (LOW) — `user_id_from_str` had no roundtrip test

CLAUDE.md: *"Every parse function must have a roundtrip test."*
`user_id_from_str` had zero references in `tests/tcyr/`, unlike the other
four `*_from_str` parsers (2–4 test files each). It is a thin delegation
to `agent_id_from_str`, so the risk was low — but the delegation is
exactly what an accidental edit to the `user_id_*` alias block would
break silently.

**Fix (v1.3.7):** roundtrip and reject-garbage tests added.

### F-020 (INFO) — `secret_metadata_new` over-allocated by 16 bytes

Confirmed and quantified from the v1.3.0 deferred list.
`secret_metadata_new` allocated **72 B** (9 slots) and wrote all nine,
but only offsets 0, 8, 16, 32, 40 and 48 have accessors. Offsets 24, 56
and 64 were zeroed and then unreachable. No caller writes these records
by raw offset (checked across `src/`), so the allocation is private to
the file.

**Fix (v1.3.7):** shrunk to **56 B** — the smallest size still covering
the highest accessed field (`owner` at 48) — and the two now-out-of-range
stores removed. Offset 24 stays zeroed: it is an interior hole, so
removing it would mean renumbering every accessor for no benefit.

The v1.3.0 deferred list gated this trim on a cross-consumer check,
because an external consumer writing offsets 56/64 by raw pointer would
get heap corruption from a smaller allocation. That check was performed
rather than waived: grepping all eleven consumer repos for `smeta_` /
`secret_metadata` returns **zero references** — no consumer uses
`SecretMetadata` at all — so the layout is private to this file and the
shrink cannot affect anyone. (The superficially similar
`store64(m + 8, …)` hits in `mneme/src/store_manager.cyr` are that
project's own records, unrelated to this type, and mneme is not an
agnostik consumer.)

### F-021 (MEDIUM, contract) — `SecretMetadata.expires_at` and `.owner` can never be set

Found while confirming F-020, and the more consequential half of it.
`SecretMetadata` has **six getters and zero setters**, and the
constructor writes `0` to both `expires_at` (offset 16) and `owner`
(offset 48). There is no code path in the library that can ever give
either field a non-zero value.

**Failure scenario:** `smeta_expires_at(m)` always returns `0`. A
consumer implementing secret-rotation or expiry enforcement reads `0`,
interprets it as "no expiry set" (the only sane reading of zero), and
concludes the secret never expires — for **every** secret, permanently.
In a secrets type this is a security-relevant footgun: the API advertises
an expiry concept it cannot actually express. `owner` has the same shape,
weakening any ownership-based access check built on it.

**Not repaired in v1.3.7.** The fix is either setters (additive API) or
a wider constructor signature (breaking). Both belong in **v1.4.0**;
pinned in the roadmap alongside F-018. Interim guidance recorded for
consumers: do not treat `smeta_expires_at` as authoritative — it is
always `0` in every released version to date.

## Verified sound (negative results)

These were examined closely and found correct. Recorded so the next pass
does not re-derive them.

- **Sub-byte struct widths.** `InjectionScores` (`alloc(5)`, five `i8`)
  and `AcceleratorFlags` (`alloc(9)`, nine `i8`) — every accessor and
  setter uses `load8`/`store8`, and the highest offset touched is
  exactly `size - 1` in both. No raw `store64` bypass anywhere: the
  `load64`/`store64` occurrences near them (`vresult_injection_scores`,
  `adev_flags`) read and write the *pointer* to the struct, not its
  fields. The v1.1.1 narrowing is clean.
- **Protobuf varint encoding.** `_proto_varint`'s
  `n = (n >> 7) & 0x01FFFFFFFFFFFFFF` looked like it might truncate the
  top bits of a sign-extended shift and emit a corrupt varint. It does
  not: the mask exactly emulates a logical shift. Modelled against
  canonical protobuf encodings across `0`, `1`, `127`, `128`, `300`,
  `2^31-1`, `2^56-1`, `2^57-1`, `2^63-1`, `-1`, `-2` and `-2^63` —
  **byte-identical in every case**, including the 10-byte encodings for
  negatives. The header comment's claim is accurate.
- **Syscall surface.** All 10 `syscall(` sites enumerated: six in
  `_fill_random` (getrandom/open/read/close/write/exit) and four
  `write(2)` to stderr in `src/error.cyr`. Argument order and count are
  correct at every site. Unchecked returns are limited to `close(2)` and
  the stderr writes, where failure is genuinely inconsequential. The one
  defective error path was F-014.
- **No command injection, no path traversal.** Zero `sys_system` in
  `src/`; the only file path is the fixed literal `"/dev/urandom"`, built
  from no external input.
- **F-001..F-013 re-verified.** All prior findings remain closed. F-013's
  bounded separator scan in `version_from_str` still holds, and no
  unbounded `strchr`/`strlen` over a non-NUL-terminated `Str` has
  reappeared anywhere in `src/` (8 total `memcpy`/`strlen`/`strchr`/
  `strcmp` sites, all checked).
- **No stack buffers.** Zero `var buf[N]` declarations in `src/` — every
  buffer is heap-allocated, so the CI security scan's ≥64 KB
  stack-buffer rule has nothing to catch.

## Performance

The repairs add validation to `tctx_from_traceparent` (a 55-byte scan
plus two all-zero checks) and remove two stores from
`secret_metadata_new`. Neither is on a benchmarked hot path —
`traceparent_format` exercises the *formatter*, not the parser, and
`secret_metadata_new` has no benchmark.

Benchmark gate against the committed v1.3.6 baseline:
**25 checked, 0 regressions.** Most ops measured slightly faster
(`sandbox_config_default` −26.2%, `accelerator_device_full` −14.4%,
`agent_id_new` −13.8%, `trace_context_child` −9.6%).

A pre/post comparison taken earlier in the pass showed a uniform +3…12%
rise across *all* benchmarks, including ones this diff cannot touch. That
was host contention — a concurrent build on the same machine — not a
regression: the untouched control benchmarks moved as much as
(`+7.4%`) or more than the benches near changed code (`+3.2%`), and the
whole shift shrank to `+2.7%` when the sample count went from 3 to 5
runs. Recorded as a reminder that this host cannot produce trustworthy
sub-10% comparisons while another project is compiling.

## Deferred to v1.4.0

- **F-018** — `*_parse()` for all 54 enums that have `*_name()`, plus a
  table-driven `parse(name(v)) == v` test over every variant.
- **F-021** — setters for `SecretMetadata.expires_at` / `.owner` (or a
  documented decision to drop the fields and their getters).

Both are additive-API changes held out of a patch release deliberately.

## Conclusion

No CRITICAL or HIGH findings. One MEDIUM memory-safety defect (F-014) in
security-critical identifier generation is fixed; two MEDIUM
spec-compliance defects in W3C trace propagation (F-015, F-016) are
fixed; two LOW/INFO items (F-017, F-019, F-020) are fixed. Two MEDIUM
contract gaps (F-018, F-021) are documented, quantified and pinned to
the next minor rather than smuggled into a patch.

The most useful structural observation from this pass is that agnostik's
*contract* rules — every enum parseable, every parser round-trip tested,
every field settable — are not mechanically enforced anywhere, which is
how a 58-enum, zero-parser gap persisted through eight releases. The
v1.4.0 plan therefore includes the table-driven test that makes the
invariant self-policing, not just the 54 functions.

886 assertions across 16 test files pass; lint/fmt/vet clean; API surface
unchanged at 871 fns; benchmark gate 0 regressions.
