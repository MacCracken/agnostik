# Agnostik Security Audit — 2026-09-23 (v1.6.2 toolchain refresh)

**Pass type:** pre-release security pass per CLAUDE.md §"Security Hardening
(before every release)", scoped to a toolchain bump.
**Scope:** every `syscall(` site in `src/`, judged against **every target the
pinned toolchain can build** (x86_64-linux, aarch64-linux, agnos and Windows
cross-built here; macOS from its syscall tables) rather than x86_64-linux
alone; the re-vendored stdlib; the CI toolchain gates.
**Toolchain:** cyrius `6.6.2` → `6.6.6`.

Two findings, both in `_fill_random` — the CSPRNG behind `agent_id_new`,
`user_id_new`, `trace_id`/`span_id` generation. **F-022** is fixed in v1.6.2.
**F-023** was deferred at the cut, because fixing it was a design choice rather
than a spelling change. It was fixed after the cut, under `[Unreleased]`, by
removing the fallback (option 2); see its **Resolution** below.

## Threat model

Unchanged from [`2026-08-24-audit.md`](2026-08-24-audit.md): untrusted JSON /
version / UUID / traceparent input crossing the serde boundary, plus the one
syscall surface that touches external state — the CSPRNG and the fatal
`stderr` message. The earlier sharpening still holds: identifiers back
authorisation in aegis and sigil, so an entropy-path defect is
security-relevant, not cosmetic.

What this pass adds is **target portability as an attack-surface axis**.
Cyrius passes a raw `syscall(N, …)` number through to the target's kernel
unless its backend translation table (ESYSXLAT) carries a row for it. The
2026-08-24 pass verified "argument order and count are correct at every site"
— true, but only for x86_64-linux numbering, which is the one target where a
raw number cannot be wrong.

## Findings

### F-022 (MEDIUM) — `_fill_random` reached `getrandom` by its raw x86_64-linux number

`src/types.cyr`, primary entropy path:

```cyrius
var got = syscall(318, buf, n, 0);
```

318 is `getrandom` on x86_64-linux and on no other target:

| target | what raw 318 did | consequence |
|---|---|---|
| x86_64-linux | `getrandom` | correct |
| aarch64-linux | unassigned → `-ENOSYS`, every call | the `/dev/urandom` fallback ran on **every** ID — 4 syscalls instead of 1, and in a sandbox that denies opening `/dev/urandom` the fail-loud path exits 70 |
| agnos | no syscall 318 (agnos `getrandom` is #45; its table ends at #97) | per the stdlib agnos peer's header, an unknown number "falls THROUGH the dispatch chain and the caller reads the fall-through value as DATA" — undefined |
| Windows | unrouted → `-ENOSYS` (per the compiler's PE routing note) | no `/dev/urandom` either, so every ID generation exits 70 |
| macOS | rewritten by ESYSXLAT to `getentropy`, which returns `0` on success (per the stdlib's `syscalls_linux_common.cyr` note) | `0 != n` reads as failure, so the `/dev/urandom` fallback ran on every ID |

**Evidence (aarch64, executed).** `qemu-aarch64 -strace` on a probe that calls
`agent_id_new()` three times, before the fix:

```
Unknown syscall 318
openat(AT_FDCWD,"/dev/urandom",O_RDONLY) = 3
read(3,0x7f0e50000000,16) = 16
close(3) = 0
```

— once per ID. The IDs themselves were random (the fallback read the kernel
CSPRNG), so on aarch64 this is an availability and cost defect, **not** an
entropy weakness. After the fix: `getrandom(0x7fa9d3600000,16,0) = 16`, once
per ID. The agnos, Windows and macOS rows come from the stdlib's syscall
tables and the compiler's routing note; none of those targets was executed
here.

**Why it went unseen.** The compiler's raw-literal diagnostic (since cyrius
6.5.51) fires on every aarch64 build of this tree —
`raw syscall 318 is x86_64 'getrandom'; on ELF-aarch64 that number is not a
syscall at all` at the 6.6.2 pin, and `… is unassigned …` at 6.6.6 — but CI's
aarch64 cross-build never ran. It probed `$HOME/.cyrius/bin/cc5_aarch64`;
cyrius renamed `cc5` → `cycc` at 6.0.0, the `cc5_*` compat symlinks came only
from its `install.sh` (dropped at 6.1.1), and no 6.x release tarball — the
thing CI unpacks — ships the old name (checked 6.0.14, 6.0.26, 6.6.6). So the
step skipped, with a `::warning::` nobody read, on every pin since agnostik
1.2.3. cyrius 6.6.4's release notes named this site explicitly ("a one-line
`SYS_*` spelling at the next bump").

**Fix.** `var got = sys_getrandom(buf, n, 0);` — the stdlib's portable CSPRNG
primitive, defined in every target's peer: `getrandom` 318 / 278 on the two
Linux arches (via `syscalls_linux_common.cyr`), #45 on agnos, `ProcessPrng` on
Windows, and on macOS `getentropy` with its `0` success return normalised to
the byte count.

The upstream note suggested spelling it `SYS_GETRANDOM`. That is *not* used:
it fails to compile for Windows (`undefined variable 'SYS_GETRANDOM'`), whose
peer defines no such constant, and it would leave macOS reading getentropy's
`0` as a short read. Both spellings are identical on the Linux targets.

**x86_64-linux effect.** Same syscall, same arguments; the binary changes only
by the wrapper call. The wrapper's `r == 0 → len` branch cannot fire on Linux
for `n > 0`. Interleaved A/B benchmarking puts the call inside layout noise —
see the CHANGELOG `[1.6.2]` Performance section.

**Severity: MEDIUM** — specific conditions (a non-x86_64-linux target), on the
identifier path that authorisation decisions rest on. It is undefined behaviour
on agnos, which is the platform this library exists to serve.

### F-023 (LOW, fixed after the cut — unreleased) — the `/dev/urandom` fallback and fail-loud exit still used raw x86_64-linux numbers

The rest of `_fill_random`:

```cyrius
var fd = syscall(2, "/dev/urandom", 0, 0);     # open
var r = syscall(0, fd, buf + off, n - off);    # read
syscall(3, fd);                                # close
syscall(1, 2, msg, strlen(msg));               # write
syscall(60, 70);                               # exit
```

- **aarch64-linux:** routed by ESYSXLAT — verified in the trace above
  (`openat`/`read`/`close`).
- **Windows:** routed — the compiler's PE note lists 0, 1, 2, 3 and 60.
- **agnos:** not routed, and no diagnostic fires for `--agnos` builds. In the
  agnos table these numbers are `SYS_GETPID` (2), `SYS_EXIT` (0),
  `SYS_SPAWN` (3), `SYS_WRITE` (1) and `SYS_WINSIZE` (60). So if the primary
  path ever failed on agnos, `open` would return the caller's pid as an "fd"
  and the first `read` would be `exit(pid)`. Read from the table, not executed.

**Reachability after F-022:** only if `sys_getrandom` fails. On agnos that
means getrandom #45 failing for a valid 16-byte heap buffer, which its peer
documents as "never hands back a zeroed buffer" and returning `-1` only for a
bad user range. Latent, hence LOW.

**Deferred at the cut** because the fix was a choice for the maintainer:

1. Route through the stdlib wrappers. `sys_read` / `sys_close` / `sys_write` /
   `sys_exit` have the same signature on every peer; `sys_open` does not —
   agnos takes `(name, namelen, flags)` — so the open needs an agnos arm.
2. Drop the `/dev/urandom` fallback now that `sys_getrandom` covers every
   target (Linux has had `getrandom(2)` since 3.17), keeping only the
   fail-loud path, spelled `sys_write` / `sys_exit`.

Option 2 is simpler and removes the only file path in `src/`. Either is a
behaviour change for kernels without `getrandom`, so it wants its own slot
rather than a toolchain patch.

**Resolution (after the cut, under `[Unreleased]` in the CHANGELOG).** The
maintainer chose option 2. The fallback is removed: if `sys_getrandom` does not
return `n`, `_fill_random` writes its message with `sys_write` and exits 70
with `sys_exit`. Option 1's agnos arm could never have succeeded: the agnos
kernel implements no `/dev/urandom` (its source names no `/dev` path at all),
and Windows has none either.

- **agnos, disassembled.** The 1.6.2 `--agnos` binary's `_fill_random` loads
  2, 0, 3, 1 and 60 straight into `syscall`, which confirms the table reading
  above. The fixed binary's `_fill_random` issues no syscall itself; its
  callees load 45 (getrandom), 1 (write) and 0 (exit). Not executed on agnos.
- **x86_64, executed** under a seccomp filter that fails `getrandom` with
  `ENOSYS`. Before the fix, a probe calling `agent_id_new()` three times got
  its IDs from `/dev/urandom` and exited 0. After it, the probe prints the
  message and exits 70, and a `qemu-x86_64 -strace` of the run shows no `open`.
- **aarch64, `qemu-aarch64 -strace`:** one `getrandom(…,16,0) = 16` per ID,
  as after F-022.

The behaviour change is the predicted one: Linux < 3.17, and sandboxes that
deny `getrandom` but allow opening `/dev/urandom`, now exit 70 on the first ID
instead of reading the fallback. `src/` opens no files, and its only raw
syscalls are `error.cyr`'s four stderr writes, verified sound below.

*Noted, not changed:* on Linux `sys_exit` is `exit(2)`, which ends only the
calling thread, as the raw 60 did. On agnos, Windows and x86_64 macOS the
exit ends the process. So in a multi-threaded Linux consumer the fail-loud
path ends the thread that asked for an ID, not the process. The stdlib's
`sys_exit_group` would end the process; switching to it is a separate
behaviour change.

## Verified sound (negative results)

- **`src/error.cyr`'s four `syscall(1, 2, …)` stderr writes** are correct on
  every target: 1 is `write` on x86_64-linux and on agnos, and is routed on
  aarch64 and Windows.
- **Vendored stdlib.** All 32 `lib/` files are byte-identical to the 6.6.6
  snapshot. The published `cyrius-6.6.6-x86_64-linux.tar.gz` matches its
  `.sha256` sidecar, and its `lib/` plus `cycc`, `cycc_aarch64`, `cyrius`,
  `cyrfmt`, `cyrlint` and `cyrius_api_surface` are byte-identical to the local
  install — so local results predict CI. The git-tracked `lib/keccak.cyr` is
  unchanged by the bump.
- **The build does not read `./lib/`.** The 6.6.6 binary is byte-identical
  whether built against the stale 6.6.2 `lib/` or the re-synced one.
- **CI security scan** (run locally, verbatim): no raw `execve`/`fork`/`clone`,
  no `sys_system`, no `/etc` / `/bin` / `/sbin` literals, no stack buffer
  ≥ 64 KB.
- **No surface change.** 916 public fns, matching `docs/api-surface.snapshot`;
  no struct-layout or wire-format change.
- **F-001..F-021** remain closed.

## Toolchain observations (not findings)

Recorded so the next pass does not re-derive them:

- **No raw-syscall diagnostic on `--agnos`.** The aarch64 diagnostic caught
  F-022; nothing would have caught F-023, although agnos numbering diverges
  from x86_64-linux further than aarch64's does. Worth filing upstream.
- **`cyrius update` on a project with no `[deps.NAME]` entries** copies the
  whole snapshot — 111 files, including an untracked `lib/unicode/` that the
  `lib/*.cyr` ignore rule does not cover — instead of the declared subset
  `lib sync` vendors. Reverted here; `lib sync` + `deps` is the correct refresh.
- **`lib/bench.cyr` (6.6.5 accounting):** `min`/`max` count only windows that
  clear a 100 × (clock floor + tick) resolution bar, while `avg` counts every
  window. Rows whose window sits near the bar can print `avg < min`
  (`message_build_3turn`, `resource_limits_from_json`). The regression gate
  reads `avg` only, so it is unaffected.

## Conclusion

No CRITICAL or HIGH findings. One MEDIUM portability defect on the identifier
entropy path (F-022) is fixed with the stdlib's portable primitive and verified
by execution on aarch64. One LOW latent defect on the same function's fallback
(F-023) was documented with two fix options at the cut, and fixed after it by
removing the fallback (option 2). The structural lesson is the same
as last pass: a gate that silently skips is worse than no gate. CI's aarch64
step printed a warning and exited 0 for the whole 6.x line, and it is
re-enabled in v1.6.2.

At the **v1.6.2** cut: 1,412 assertions across 18 test files on x86_64-linux
**and** on aarch64 (under `qemu-aarch64`); lint / fmt / vet / type-check clean;
API surface unchanged at 916 fns; benchmark gate 25 checked, 0 regressions.
