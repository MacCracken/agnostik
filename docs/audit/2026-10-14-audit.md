# Agnostik Security Audit — 2026-10-14 (v1.6.5 toolchain refresh)

**Pass type:** the pre-release security pass required by CLAUDE.md §"Security
Hardening (before every release)", scoped to a toolchain bump.
**Scope:** the cyrius security advisories published between the old pin and the
new one, judged against what agnostik actually reaches. Also the re-vendored
stdlib, the syscall sites in `src/` on every target the pin builds, the new
`cyrius.lock`, and the changed distribution sidecar.
**Toolchain:** cyrius `6.6.6` → `6.6.20`.

**No findings.** No agnostik source changed, apart from two comments. One
advisory, CYRIUS-2026-0028, reaches agnostik code, and agnostik's caller was
never exposed to it. The 1.6.5 re-vendor brings the fixed `lib/fmt.cyr` anyway.

## Threat model

Unchanged from [`2026-09-23-audit.md`](2026-09-23-audit.md). The inputs are
untrusted JSON, version, UUID and traceparent strings crossing the serde
boundary, plus the CSPRNG and the fatal stderr message. Target portability
stays an axis: a raw syscall number is judged on every target, not only
x86_64-linux.

### CYRIUS-2026-0028 and `version_to_str`

`version_to_str` (`src/types.cyr`) formats the three numeric components with
`fmt_int_buf` at `buf + pos`, which is the calling pattern the advisory
describes. Up to 6.6.17, `fmt_int_buf` built its digits from `buf + 23`
downward, so every call wrote 24 bytes at `buf + pos` whatever the number's
length.

agnostik's buffer is `alloc(128)`. The third call starts at most at `pos = 42`
(a 20-character `i64` minimum, a `.`, another 20 characters, and a `.`), so
the widest scratch write ends at `buf + 66`. Bytes past the formatted number
are scratch that the following writes overwrite in order. The prerelease and
build suffixes are bounded by `cap = 127`. A probe built the widest possible
string on both pins:

```
-9223372036854775808.9223372036854775807.-1-rc.1+sha.0123456789abcdef
```

It came out correct, 69 bytes, on 6.6.6 and on 6.6.20. 6.6.18's
`fmt_int_buf` writes exactly `len + 1` bytes, so the margin is now wider.

## Syscall sites, every target

The sites are unchanged since v1.6.3. `src/types.cyr` reaches the stdlib's
`sys_getrandom`, `sys_write` and `sys_exit`. `src/error.cyr` has four raw
`syscall(1, 2, …)` stderr writes. 1 is `write` on x86_64-linux and agnos, and
is routed on aarch64 and Windows. `CYRIUS_DCE=1` builds succeed for
x86_64-linux, aarch64, agnos and Windows, with no warning from agnostik
source. The Windows build prints one warning from the stdlib's own
`lib/syscalls_windows.cyr:436` (a one-argument `syscall 12`). 6.6.6 printed a
broader, generic routing warning for the same target. The v1.7.1 roadmap slot
moves the four raw sites to `sys_write` and gates `src/` against new ones
([ADR-003](../adr/003-roadmap-tracks-agnostik-work-only.md)).

- **CI security scan**, run verbatim: no raw `execve`/`fork`/`clone`, no

## v1.7.0 minor-cut pass (same day)

**Pass type:** the security audit every minor cut runs (CLAUDE.md §"Security
Hardening"). It is recorded here because it fell on the same date as the 1.6.5
pass above. **Scope:** the diff 1.6.5 → 1.7.0, which covers the `_stik_` helper
rename, the `ClassificationResult` setters and `scripts/consumer-sweep.sh`,

**One finding, F-025, fixed in 1.7.0.**

### F-025 (LOW, defense in depth) — agnostik's parsers could run another library's code

A consumer compiles agnostik into one unit together with every other library
it vendors. There, a same-named fn either replaces the other (same arity,
"last definition wins") or fails the build (different arity, a hard error
since cyrius 6.6.2). agnostik's private helpers had generic names. The
consumer sweep and a scan of every local AGNOS checkout found:

| Helper | Collides with | Effect |
|---|---|---|
| `_hex_nibble` | sigil, which ships in the stdlib snapshot (a copy in 60+ repos) | Same arity: in aegis, ark and mela, sigil's definition ran inside agnostik's parsers; in kybernet, agnostik's ran inside sigil's |
| `_json_int`, `_json_str` | ai-hwaccel (4 args), itihas (3 args) | Different arity: the build fails, so daimon, hoosh, stiva, kavach and agnosai, which vendor ai-hwaccel, could not vendor agnostik |
| `_hex_byte` | bote (2 args vs 3) | Different arity: the build fails |

`_hex_nibble` does the hex decoding for `agent_id_from_str`,
`trace_id_from_str`, `span_id_from_str`, `tctx_from_traceparent` and the JSON
`\u` escape decoder, all of which parse untrusted input. sigil's definition
maps characters the same way (`'0'-'9'`, `'a'-'f'`, `'A'-'F'`, else −1), so no
input parsed differently, and no exploit existed. The defect is that the
integrity of agnostik's parsers depended on another library's helper keeping
the same semantics, with nothing to notice if it changed. Hence LOW, defense in
depth.

**Fix (1.7.0):** all 21 `_`-prefixed fns in shipped modules are now
`_stik_<name>`. They are not public API (none is in
`docs/api-surface.snapshot`, and no consumer calls one). CI's "Private helpers
are namespaced" step fails on any unprefixed one, and a planted
`fn _mutant_helper` fails it. **Verified:** the consumer sweep reports 0
agnostik-involved duplicate definitions in all five consumers (4 of 5 before).

### Re-scan and new code

- `src/` has no `sys_system`, no `/etc` / `/bin` / `/sbin` literal and no stack
  buffer of 64 KB or more. The only raw syscalls are `src/error.cyr`'s four
  `syscall(1, 2, …)` stderr writes, as before. The roadmap moves them to
  `sys_write` at v1.7.1.
- **`cresult_set_level` / `_set_auto_level` / `_set_confidence`** reject a
  level outside `ClassificationLevel` and a confidence outside 0..1000 with an
  invalid-argument `Err`, leaving the result unchanged. Tested at the bounds,
  at `i64` min and max, and over a −50..1050 sweep; mutation-checked.
- **`scripts/consumer-sweep.sh`** builds and runs the consumers' code by design.
  It is a local release tool: not shipped, not in CI. Code review hardened it
  before release:
  - It refuses to run without a scratch directory. A failed `mktemp` would
    have aimed its copies and cleanup at `/`.
  - Its preflight reports the real `distlib --check` output.
  - Consumer paths come from directory discovery and are always quoted.
  - It writes only under its `mktemp -d` scratch directory.
- **F-001..F-024** remain closed.

**Conclusion: ship 1.7.0.** F-025 is fixed and gated, and the rest of the
re-scan is clean.

## v1.7.1 release pass (same day)

**Pass type:** the pre-release pass CLAUDE.md requires of every release.
**Scope:** the diff 1.7.0 → 1.7.1:
- `src/error.cyr`'s stderr writes;
- the CI security scan;
- the new `scripts/ci-install-cyrius.sh` and the two workflows that call it;
- the aarch64 CI step;
- the removal of `lib/keccak.cyr` and the relock.

**Toolchain:** cyrius 6.6.20, unchanged.

**No findings.** The release is itself hardening:

- **Syscalls, every target.** `src/` has no raw `syscall(` left. The last four,
  `agnostik_err_print`'s `syscall(1, 2, …)`, are `sys_write(2, …)`, which the
  Linux, aarch64, macOS, Windows and agnos peers all define. stderr is
  byte-identical to 1.7.0 on x86_64 and aarch64. The CI scan now fails on any
  raw `syscall(` in `src/`, which closes from agnostik's side the agnos gap the
  compiler does not diagnose (F-023's class).
- **`scripts/ci-install-cyrius.sh`.**
  - The version must match `X.Y.Z` before any network access. Path-traversal
    (`6.6.20/../../x`), shell-metacharacter (`6.6.20;id`) and short forms
    are refused.
  - Downloads use `curl -f`, so an HTTP error is an error, not a saved page.
  - `SHA256SUMS.sig` is verified against a pinned Ed25519 key, then the
    tarball against exactly one `SHA256SUMS` line, all before `tar` runs.
  - The work happens in a `mktemp -d` directory removed on exit.
  - The verified tarball has no absolute or `..` member paths.
  - A wrong key and a corrupted tarball each exit 1 with nothing installed.
  - Residual risk: a cyrius key rotation fails CI closed until the pin is
    updated. That is the intended trade, and the script and CLAUDE.md
    document the procedure.
- **aarch64 CI step.** It installs only the distribution's `qemu-user`, and
  runs the suite on code agnostik itself built.
- **Lock.** `cyrius.lock` covers the 32 vendored files. A fresh checkout
  reproduces it byte for byte, and `deps --verify` passes, 32 of 32.
- **F-001..F-025** remain closed.

**Conclusion: ship 1.7.1.**

## v1.9.0 minor-cut pass (same day)

**Pass type:** the security audit every minor cut runs. **Scope:**
- the `RestartPolicy` name/parse pair;
- doc comments on every fn (comments only, proven byte-identical in the binaries);
- the three defects the documentation pass found: the timestamp clock, the span-id byte order and
  JSON escaping.

**Toolchain:** cyrius 6.7.9, unchanged since 1.8.0, so no new advisories are in range.

**One finding, F-026, fixed in 1.9.0.**

### F-026 (LOW) — two JSON string fields were serialized unescaped

**Where:** `TelemetryConfig_to_json` (`export_endpoint`) and `AgentInfo_to_json` (`name`), both
fixed in 1.9.0. Each wrote its `Str` between two `str_builder_putc(sb, '"')` calls with
`str_builder_add`, so no character was escaped. A `"` in the value ended the JSON string early,
and what followed was parsed as JSON.

**Impact:** An agent name of `x","status":"Failed` produced a document with a second `status` key.
A consumer that serializes an `AgentInfo` built from caller-supplied input could therefore emit
JSON that misreports the agent, or that does not parse. A backslash or control character produced
invalid JSON. The endpoint usually comes from operator config, which lowers its exposure.
The injected key comes before the real one, and agnostik's own `AgentInfo_from_json` takes the
first match. So even a round-trip within agnostik read the injected status. With the raw write
restored, the test reads status 8 for an agent built as 2 (`AGENT_RUNNING`). LOW: this needs a consumer that serializes untrusted names, and none of the five current
consumers calls either function.

**Fix:** both now call the stdlib's `str_builder_add_json_str`, which escapes:
- `"` and `\`;
- `\b \t \n \f \r`;
- every other byte below 0x20, as `\u00XX`.

Output for strings with none of those bytes is unchanged, and the serde golden test still
passes byte for byte. `tests/tcyr/test_v190_fixes.tcyr` pins the exact escaped output and an
injection-shaped name round-trip. Restoring either raw write fails two of its assertions.

**Sweep:** every remaining `str_builder_putc(sb, '"')` and `str_builder_add(sb, …)` in `src/` was
read in context. None writes a caller-supplied string into JSON unescaped:
- the agent id is a UUID that `agent_id_to_str` prints in hex;
- `_stik_json_find_value` builds an internal search key, not output;
- `proto.cyr` writes protobuf bytes;
- the traceparent fields are hex.

### The other fixes, checked as new code

- **Timestamps.** The ten construction-time stamps now read `clock_epoch_ns()`: `CLOCK_REALTIME`
  on Linux and macOS, `GetSystemTimeAsFileTime` on Windows, and `sys_time_unix()` seconds on agnos.
  All go through the stdlib, with no raw syscall in `src/`. Wall time can step backwards (NTP, a
  manual set). Nothing in agnostik orders, expires or authenticates by these stamps, so the change
  places no new trust in them: they are reported, not enforced. The tests check every stamp is
  after 2020-09-13 and within 60 s of the wall clock, on x86_64 and under `qemu-aarch64`.
- **Span-id parsing.** Validation is unchanged:
  - exactly 16 characters, or `Err`;
  - each digit decoded by `_stik_hex_nibble`, with any non-hex byte rejected before it is stored;
  - one fixed 8-byte allocation.

  The loop now writes byte i from digits 2i and 2i+1 with `store8`, so no index depends on input.
- **`restart_policy_name` / `restart_policy_parse`.** Same shape as 1.8.0's pairs: integer
  comparisons, and `str_eq_cstr` against three literals. This is the pair 1.8.0 held back.
  argonaut 1.15.4 renamed its own to `argonaut_restart_policy_parse`, and kybernet 1.7.9 calls
  that. The consumer sweep finds 0 agnostik-involved duplicate definitions across the five
  consumers.
- **Doc comments.** Comments only:
  - each file, with its full-line `#` comments stripped, is byte-identical to its pre-pass copy;
  - the `CYRIUS_DCE=1` binaries are byte-identical to the pre-pass builds.

  Writing them surfaced F-026 and the two defects above. The rest of what it found are
  robustness gaps, not security findings, and are on the roadmap: getter-only fields, unset
  optional vtable slots called at address 0, process-global hand-offs and `agent_id_from_str`
  validation.

### Re-scan

- The CI security scan is clean: no raw `syscall(`, no `sys_system`, no `/etc` / `/bin` /
  `/sbin` literal, no stack buffer of 64 KB or more.
- The private-helper gate passes.
- **F-001..F-025** remain closed. **F-026** is fixed.

**Conclusion: ship 1.9.0.**

## v1.10.0 minor-cut pass (same day)

**Pass type:** the security audit every minor cut runs. **Scope:**
- the OTLP completion: `AnyValue`, Span attributes / events / links, `LogRecord_to_otlp_proto`,
  `MetricDataPoint_to_otlp_proto` and `metric_to_otlp_proto`;
- the `src/proto.cyr` rewrite to an in-place buffer;
- the Status field fix.

**Toolchain:** cyrius 6.7.9, unchanged, so no new advisories are in range.

**One finding, F-027, fixed in 1.10.0.**

### Threat model for the new code

The encoders read structs the caller built: spans, records, points and their attribute maps. They parse no
external bytes. External content can still reach them as data, for example an HTTP path stored as an attribute
string, but it is copied by length and never interpreted.

So the risks are:
- memory safety when a caller-built value is malformed;
- termination on cyclic or deep values;
- output a decoder rejects.

### F-027 (LOW, defense in depth) — the OTLP encoders could write out of bounds or read address 0 on malformed values

**Where:** `_stik_pb_bytes` and `_stik_pb_string` (`src/proto.cyr`) and `Span_to_otlp_proto`; fixed in 1.10.0.

**What:**
- **Negative length.** `_stik_pb_bytes` took a `Str`'s length as given. With a negative length, `str_new(p, 0 -
  1000)` for example, its reserve was a no-op and its copy wrote nothing, but it still added the length to the
  write position. Reproduced on the pre-fix tree, an empty buffer's position became −989, so the next field would
  have been written 989 bytes before the buffer, on the heap.
- **Null pointers.** `Span_to_otlp_proto` read a 0 span name, trace id or span id from address 0. Both
  reproduced with exit 139 (`SIGSEGV`). The null-read half is pre-existing since v1.2.0; the old
  `_stik_proto_*` helpers read the same pointers.

**Impact:** a malformed value, built by the caller, could corrupt the heap or crash the process. No agnostik
parser produces a negative-length `Str`, and none of the five consumers calls these encoders. LOW, defense in
depth.

**Fix:**
- a negative length, or a 0 data pointer, writes an empty field;
- `_stik_pb_string` treats a 0 `Str` as empty;
- `Span_to_otlp_proto` omits 0 ids, and writes a 0 name as an empty name.

`test_malformed_values` (`tests/tcyr/test_v1100_otlp.tcyr`) checks each case: the bytes written, an intact later
entry, and an untouched guard pattern. Removing any of the four guards fails the file; two of the four crash it.

### The rest of the new code, checked

- **Buffer bounds.** Every write reserves its worst case before storing, and re-reads the data pointer afterwards,
  since growth moves it:
  - a varint reserves 10 bytes;
  - a fixed64 reserves 8;
  - a bytes field reserves its (now non-negative) length;
  - opening a nested message reserves 1 byte;
  - closing one reserves `k − 1` more before shifting the body right.

  The shift copies from the end, within `[mark, len + k − 1)`, which the reserve covers.
- **Recursion.** AnyValue nesting stops at depth 16. The path buffer holds 16 slots (128 bytes), and a slot is
  written only after `depth < 16` is checked. A box already among its ancestors is a cycle and is cut. A shared,
  acyclic value is written in full each time it appears, which is the correct output.
- **Keys.**
  - cstr keys are NUL-terminated by the map's own contract, and the cstr comparator stops at the first difference
    or the NUL.
  - The Str comparator is bounded by both lengths.
  - The key type is read from the stdlib map header's key-type word at +24, which has no accessor. A test pins
    both key types, so a layout change in the stdlib fails a test rather than misreading keys.
- **`metric_to_otlp_proto`** validates kind and temporality before it writes anything, so an `Err` leaves the
  caller's builder untouched.
- **Output a decoder rejects.**
  - Strings are written as given. Protobuf requires UTF-8 in `string` fields, and a strict decoder may reject a
    message that carries invalid UTF-8. That is an availability concern for telemetry, not memory safety, and
    roadmap v1.12.0 carries it.
  - The Status fix (field 1 → 3) is a correctness fix. The old bytes decoded as an unknown field, not as anything
    harmful.

### Re-scan

- The CI security scan is clean: no raw `syscall(`, no `sys_system`, no `/etc` / `/bin` / `/sbin` literal, no
  stack buffer of 64 KB or more.
- The private-helper gate passes: every new private fn is `_stik_`-prefixed.
- **F-001..F-026** remain closed. **F-027** is fixed.

**Conclusion: ship 1.10.0.**

## v1.11.0 minor-cut pass (same day)

**Pass type:** the security audit every minor cut runs. **Scope:** the contract gaps from the v1.9.0
documentation pass:
- checked trait dispatch (`_stik_slot_fn` / `_stik_dispatch0..2`), with the new `as_query`, `ss_rotate`,
  `ss_search_by_tag`, `audit_sink_has` and `secret_store_has`;
- the argument-passing hand-offs;
- `agent_id_from_str`'s separator check;
- 91 setters and 2 getters;
- four Landlock rights and `rlimit_type_resource`.

**Toolchain:** cyrius 6.7.9, unchanged, so no new advisories are in range.

**No findings.**

- **Dispatch.** `_stik_slot_fn` returns 0 for a 0 trait object, a 0 vtable or a 0 slot, and no dispatcher calls
  through a 0 pointer any more. A slot index is read only within its own vtable:
  - the dispatchers pass their module's slot constants;
  - `audit_sink_has` and `secret_store_has` reject a slot outside `AS_APPEND..AS_SEAL` /
    `SS_GET..SS_SEARCH_BY_TAG`.

  Passing one trait's object to another trait's dispatcher can still read past a smaller vtable. That is the same
  type confusion `trait_call*` always allowed, a caller error, and not new.
- **Calling convention.** The hand-offs call `fncall3`. On every target the cyrius stdlib supports, arguments
  1–3 travel in registers: rdi / rsi / rdx (x86_64 SysV, which agnos uses too), x0..x2 on aarch64, and rcx / rdx /
  r8 (MS x64). So a callback written with two parameters ignores the third without unbalancing the stack. Tested
  on x86_64 and under qemu-aarch64; Windows is build-checked only.
- **Setters.** Each stores as given, like every earlier setter, so a caller can now store any value in 91 more
  fields. The paths that newly reach a consumer were checked:
  - **JSON:** no serializer writes a newly settable string raw. The derive structs with new setters
    (`ResourceUsage`, `AgentStats`, `EdgeResourceOverrides`) hold integers only. `TelemetryConfig_to_json` escapes
    the endpoint (F-026).
  - **traceparent:** `tctx_to_traceparent` masks the flags with `& 0xFF` before `_stik_hex_byte` indexes its
    lookup table. Before v1.11.0 the flags were always 0..255, because they came from the constructor or the
    validated parser. A set value cannot index past the table.
  - **OTLP:** `span_set_dropped_*` values go out as varints; a negative value writes 10 bytes, which is valid wire
    format. `mdp_set_temporality` values are validated by `metric_to_otlp_proto`, which already returns `Err` for
    an unknown temporality.
- **`agent_id_from_str`** reads exactly 36 bytes, after checking the length, and now rejects a non-dash at the
  four separator positions. The v1.1.2 fuzz target still runs against it.
- **Landlock values** come from linux-api-headers 7.2 (`linux/landlock.h`), and the RLIMIT numbers from
  `asm-generic/resource.h`. Both are pinned by tests.

### Re-scan

- The CI security scan is clean: no raw `syscall(`, no `sys_system`, no `/etc` / `/bin` / `/sbin` literal, no
  stack buffer of 64 KB or more.
- The private-helper gate passes: the four new private helpers are `_stik_`-prefixed.
- **F-001..F-027** remain closed.

**Conclusion: ship 1.11.0.**

## v1.12.0 minor-cut pass (same day)

**Pass type:** the security audit every minor cut runs. **Scope:**
- the UTF-8 guarantee for OTLP `string` fields (`_stik_utf8_step`, `_stik_utf8_fixed_len`, `_stik_pb_copy_utf8`,
  `_stik_pb_text`, `_stik_pb_any_string`);
- the Resource / InstrumentationScope encoders and the three export-request builders;
- histogram data points and packed fields;
- exemplars and start times;
- the span status message;
- the split of `metric_to_otlp_proto` into a check and a writer.

**Toolchain:** cyrius 6.7.9, unchanged, so no new advisories are in range.

**No findings.**

- **UTF-8 scanning** reads only inside the source:
  - `_stik_utf8_step` reads `p[i + k]` only while `i + k < len`;
  - the word fast paths `load64(ptr + i)` only when `i + 8 <= len`;
  - `_stik_pb_copy_utf8` reserves `len` bytes before copying, stores a word only within them, and on an ill-formed
    sequence rewinds the buffer length to where the field began, so a partial field never remains.
- **The sanitizing path** reserves the length `_stik_utf8_fixed_len` computed and writes exactly that many bytes.
  The two walk a string with the same step function, and the differential tests check each length prefix against
  its body, across 40,000 strings with 0 mismatches against Python.
- **Strings reaching consumers.** Every OTLP `string` field is now valid UTF-8 (ADR-006). An attacker-influenced
  attribute value or log body with invalid bytes can no longer make a strict collector reject the whole export
  request. That was an availability problem for telemetry, not memory safety. It is fixed rather than carried.
- **Envelopes.** The request builders nest five deep inside one buffer. Each `_stik_pb_open` / `_stik_pb_close`
  pair is closed LIFO. The two envelope marks are packed into one word as `outer * 2^32 + inner`, which holds for
  any buffer under 4 GiB; the bump allocator cannot reach that in one encode.
- **Histograms.** The shape check runs before anything is written:
  - no negative count or bucket count;
  - bounds only with buckets;
  - one more bucket than bounds;
  - buckets summing to the count.

  The packed fields write `8 × count` bytes from the vecs' own lengths. The bucket sum is an i64 and can wrap
  for absurd counts, which could let a mismatched point pass. That is a semantic oddity in caller data, not a
  memory issue.
- **Null handling.** `metric_to_otlp_proto` with a 0 descriptor now returns `Err`; before, it read address 0. A 0
  resource or scope is omitted from a request, and 0 entries in the span, record and metric vecs are skipped.

### Re-scan

- The CI security scan is clean: no raw `syscall(`, no `sys_system`, no `/etc` / `/bin` / `/sbin` literal, no
  stack buffer of 64 KB or more.
- The private-helper gate passes: the 19 new private helpers are `_stik_`-prefixed.
- **F-001..F-027** remain closed.

**Conclusion: ship 1.12.0.**
